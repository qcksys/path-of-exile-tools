# Crafting parity audit

Audit date: 2026-10-07. Scope: calculator, process simulator and item emulator for **both PoE 1 and PoE 2**, with build-extracted game records and the user's supplied Memory Strand model. The identified reference workflows are implemented within the revised scope and documented probability models below. The implementation history in [crafting-implementation.md](crafting-implementation.md) records individual changes and model limitations. This audit does not claim exhaustive comparison of every rendered variant or knowledge of undisclosed server probabilities.

Scope change, 2026-10-07: synthesis and random PoE 2 Delirium allocations are out of scope. Delirium weights remain unknown; existing manual allocations remain supported. The user authorized PoE Wiki exceptions for Grasping Mail weights and Heist eligibility, and selected manual Heist enchantments with unknown odds rather than random estimates. These decisions supersede the earlier source-blocker statements below.

## Wiki exceptions and current scope

Grasping Mail uses the [wiki revision 1697822](https://www.poewiki.net/index.php?title=Grasping_Mail&oldid=1697822): 25 Breach modifiers mapped to existing build IDs and their wiki weights. Modern recipes select each Breachlord proportionally to the supplied 60-ring composition, then weight eligible modifiers within that lord. Legacy recipes use the combined weights. Conflicting groups and full affix sides are excluded before selection. The 1/2/3-special-mod count uses the wiki's approximate 50%/33%/17% distribution; remaining ordinary affixes use the existing rare-item model. This is a disclosed probability model, not newly extracted server data. The generated rare-item price represents the whole recipe. Special modifiers can be edited, targeted, imported and retained by follow-up crafts, but ordinary rerolls cannot generate them. Transfers use the existing recombination model with Breach modifiers marked exclusive; its existing restrictions on multiple exclusive inputs still apply.

Manual Heist selection uses [Tempering revision 1681190](https://www.poewiki.net/index.php?title=Tempering_Orb&oldid=1681190) and [Tailoring revision 1681191](https://www.poewiki.net/index.php?title=Tailoring_Orb&oldid=1681191). The browser export now includes 136 weapon and 54 body-armour enchantments from the build. The 3.29 removal of white-socket and all-one-color enchantments is applied even where an old wiki table row remains. Modifier identities, stat values and text remain extracted; wiki eligibility and effect-tag semantics are explicit exceptions. No random weights are assigned. Manual selection spends no currency and participates in history, saved items, targets and subsequent simulation. Modifier magnitudes, attribute requirements, additional crafted capacity, maximum sockets and guaranteed links affect the modeled item. Color restrictions remain visible text because this model does not store socket colors. Tempering/Tailoring random crafting stays unavailable with unknown odds, as requested.

The earlier missing source mapping no longer blocks the agreed scope. Validation of this increment is recorded at the end of this document.

## Item flags and state-editing boundaries

The public packages' `ItemFlags` definitions explicitly make Corrupted, Mirrored, PoE 1 Split and PoE 2 Sanctified usable as requirements. Their item action menu dispatches `corrupt`/`uncorrupt`, `mirror`/`unmirror`, `sanctify`/`unsanctify` and `split`/`unsplit`, and updates either the crafting item or the simulator's starting item. The handlers, not just the feature-list text, establish this requirement.

The workbench now edits all four flags through a shared validated operation, alongside rarity, level, properties and influences. Corrupted, Mirrored and Sanctified replace one another when enabled; Split is independent and specific to PoE 1. The canonical item and target schemas carry the applicable flags through item text, inventory, projects and snapshots. All conditions support Any, required presence and required absence, including nested expressions and process routes. Game-inappropriate states and requirements are rejected, including an explicit false requirement for the other game's flag.

Manual edits preserve underlying rolls without consuming randomness or charging currency. Clearing Sanctification or corruption removes the corresponding value multipliers; clearing corruption also clears twice-corruption, Putrefaction and corruption-source markers. The resulting item must still validate: intrinsic corruption, corruption-only implicits, extra affixes or values that require corruption cannot be made legal by clearing a flag. Destroyed items and unresolved Allflame copies cannot be edited. These restrictions preserve the application's valid-item model and are stricter than the reference's bare flag assignments. The interface explains the multiplier and corruption-only-outcome behavior. Undo/redo restores complete previous states and spending remains unchanged. No additional game dataset or extraction change is needed for these state controls.

## Clearing history and spending

Both inspected public packages implement `Calculator.clearHistory` through `Emulator.resetHistory`; the latter clears recorded actions and spending without changing the item. The workbench now provides the equivalent separate control, alongside Reset. Clearing retains the current selected undo state and project configuration, removes redo, resets craft counts/currency spending and establishes one retained starting item. The seed starts again from the unchanged project seed. Pending Allflame copies remain available and charge their craft once on selection. Running process/calculation workers are stopped and stale callbacks are ignored.

Seven new workbench cases and seven affected existing flag/history/save cases pass across three files. TypeScript, repository lint, diff checks and the production build pass, with both catalogs regenerated through package verification. These history cases also passed in the subsequent full run described above. This is a UI/history operation and introduces no game records or extraction changes. Live-browser coverage is not claimed for this increment.

No new game records or third-party data are needed for this operation.

## Crafting after a retained reveal

Both games now allow further supported crafts and manual edits while reveal offers are pending. Validating offered choices captures `offeredOn`, an item snapshot derived from the canonical item fields, including socketed Jewel state. This also normalizes older saved pending items before editing. This snapshot validates the original offers against their original eligibility even after affixes, augments or other item properties change. The current item must still satisfy the reveal source's class/level rules. The context has bounded, nonrecursive structure and cannot belong to another base or exist without offers. Current and historical items are both validated with extracted records.

Later crafts use their ordinary pools; retained offers do not remove potential outcomes from those pools. If a new modifier blocks an offered choice, the offer remains visible with its original probability of being present, but selection is disabled and the engine rejects choosing it before consuming randomness. Removing the blocker makes it selectable again. Automatic reveal preferences and fallback consider currently eligible offers; `skipOnMiss` can keep an offer pending. Echoes rerolls against the current item, replaces the superseded context with the new offer context, and retains its already-paid cost. Removing the veiled modifier or generating a new item removes the reveal state.

The conflict guard preserves this application's valid-item rule; the original simulator's direct assignment is not used to introduce duplicate modifier groups. The snapshot and offers survive project JSON, inventory and history. Unrevealed item-text export retains its existing explicit JSON-export requirement instead of dropping hidden state.

## Bench replacement and conflict handling

The inspected beta PoE 1 `benchcraft` handler removes an existing craft before attempting its replacement when the item has single-craft capacity. It charges removal even when the new modifier is blocked. With multiple-craft capacity, it retains existing crafts and rejects additions at capacity. The original simulator additionally exposes a skip-on-conflict option. The shared engine now implements these ordinary workflows with the build's removal recipe, new-modifier recipe and costs. Normal bases become magic after a successful addition. Fractured crafts remain protected.

`skipOnConflict` skips only capacity, open-slot, duplicate-modifier and modifier-group conflicts. It leaves any completed removal and cost intact, and process conditions examine that resulting item. Invalid recipes, wrong item classes and forbidden item states still fail. Without skipping, a typed bench conflict carries completed removal state and spending into failed process/sampled results and emulator history. Undo/redo restores the item and costs. Single-method exact calculation reports the conflict instead of a successful calculation. Exact cost quotes share the same deterministic bench preparation; worker spending sums repeated ingredient IDs. Price controls include possible removal ingredients before crafting.

The beta's flask handler separately charges the extracted Remove Enchantments recipe when replacing an Instilling enchantment at the bench. ## Memory Strand acceptance details

The user-supplied numbered mechanics are covered by the following current code and tests:

1. `memoryTierCount` uses integer-equivalent arithmetic for `floor(100 * (tiers - 1) / (2.5 * strands + 147.5)) + 1`, with zero strands preserving all tiers. `crafting-memory.test.ts` checks every supplied breakpoint, including the theoretical 102/122 rows.
2. Foulborn adds 75 to the denominator rating when strands are present and uses the standalone rating without strands. Tests cover both behaviors and item-level eligibility.
3. `unravellingOutcomes` uses the extracted total weight on the modifier's side and the sum of eligible higher-tier weights. The probability is clamped at one. Tests check 15, 31 and 32 strands, influences, independent modifiers and the extracted wand generation-weight multiplier.
4. Destination weights sum each tier's own weight and all eligible higher-tier weights, implementing the user's 9/27 correction. Unequal-weight tests distinguish this from multiplying each tier's own weight by a tier index.
5. Remembrance uses the supplied research histogram as an empirical model, with all 91 modeled strand values and bucket mass tested. The client does not supply these observed frequencies; the interface and documentation distinguish them from extracted records.
6. Imprints, crafted results, item text, saved projects, target conditions, exact processes, simulation and history retain strand state. Extracted currency-action costs and the separate estimated consumption rule apply after a successful craft.
7. Ordinary equipment identification applies the same tier filtering without consuming strands. Its separate unidentified template avoids treating an identified empty rare item as unknown.
